# 首版需求与架构

## 目标

用一套可解释、可复现、能实际操作的演示系统，证明零售经营分析、算法应用、内容流程、证据质量与项目管理思路。优先完成一个端到端案例，不声称达到生产系统成熟度。

## 业务案例

虚构零售企业，6家门店、4个品类。经营快照截至2026-11-22。最近28天东区部分商品存在零库存快照，模拟成交率下降，零食折价促销影响商品毛利。系统应呈现这些事实，同时保留原因假设与验证计划。

## 数据模型

- stores：门店、区域、面积与人数。
- products：SKU、品类、标价与固定成本。
- members：匿名演示会员、注册日、模拟偏好。
- orders / order_items：订单头、成交单价、数量和退货数量。
- traffic：门店日客流。
- inventory：门店SKU日库存快照。
- prices：同规格竞品周采样。
- evidence：原始信源组、文本、日期、有效期与来源类型。
- model / evaluation：训练快照与时间切分离线评估。
- plan / tasks / script：跨模块共享的促销方案、项目任务与审核脚本，保存于浏览器。

所有交易金额以分为单位。净销售额与商品成本均依据退货后净数量计算。退款归属原订单日期，不模拟实际退款流水日期。

## 架构

Python固定种子生成数据，写入SQLite与同源静态数据快照；Node测试负责验证JavaScript计算。浏览器调用共享core.js进行分析、推荐、定价与证据检查，app.js负责界面与模块联动。浏览器Canvas与MediaRecorder在用户触发后生成WebM视频；独立脚本提前生成可播放MP4。

本地HTTP服务只绑定127.0.0.1，可选通过进程环境变量调用外部模型润色脚本。托管部署为静态应用，核心演示不需要服务器、密钥或联网。

SQLite是可审查的数据交付件，当前界面读取data.js快照，未在运行时查询SQLite。任务与审核记录没有服务端多人同步。

## 指标与算法取舍

- 全店与门店汇总、商品汇总、趋势必须能相互对账。
- 销售采用固定顺序客流→转化→客单价的代数分解，贡献随顺序变化，不视为因果。
- RFM：R为距最近购买天数，F/M使用近90天；明确规则分层，不输出伪造的流失概率或LTV。
- 推荐：购物篮共现余弦相似度、购买强度与热门回退。训练与测试按时间分开；线上展示额外过滤最新库存。
- 促销：恒定价格弹性假设与库存上限，弹性和基准销量由用户输入，比较费用后贡献及原价情景。
- 研究：日期检查、同源去重、引用与报告模板。没有实时检索和事实真实性自动认证。
- 内容：价格引用商品或当前活动记录；改动配置后需重新核对。模板和真实模型输出明确标记。

## 后续生产化优先级

1. 确认业务主体、品类、渠道与业务负责人，接入POS、商品、会员及库存数据。
2. 建立数据质量、退款流水归属、变动成本及指标版本管理。
3. 接入可授权的数据源与检索服务，完善同款匹配和来源审计。
4. 引入真实行为埋点与实验分流，离线评估后通过对照试点验证净毛利和负向指标。
5. 建立内容素材权限、生成式模型适配、人工审核与交付成本记录。
6. 将浏览器状态迁移至带身份权限的持久化服务，增加任务、模型调用和数据变更审计。
